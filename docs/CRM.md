# Kamo Autoservice CRM — модуль Kontrolla

CRM встраивается в существующий Kontrolla как отдельный модуль, включаемый
для конкретной организации. Один бэкенд, один фронтенд, одна БД.

## Принципы

- Код модуля: `backend/src/modules/crm/`, `frontend/src/modules/crm/`; API под `/api/crm/*`.
- Каждый CRM-роут: `requireAuth` → `requireModule('crm')` → проверка прав.
- Таблицы с префиксом `crm_`. Существующие таблицы меняются только добавлением.
- Финансовые операции — функции PostgreSQL (одна транзакция), журнал операций
  неизменяемый: исправление = сторнирующая операция.
- Все действия пишутся в `audit_log`.
- Периоды отчётов («сегодня», «месяц») считаются в `organizations.timezone`
  (по умолчанию `Asia/Tashkent`) через `backend/src/lib/time.js`.

## Бизнес-решения

- Выручка признаётся при выдаче автомобиля (статус «Выдан»). Оплаты до выдачи —
  авансы. Долг клиента = сумма выданных заказов − оплачено.
- Заявка (обращение) — отдельная сущность; статус воронки хранится у заявки.
- Валюты UZS и USD; отчёты в UZS по курсу, зафиксированному в операции.
- Процент мастера настраивается для пары «мастер × категория» (база и ставка).
- Штрафы Kontrolla в зарплату не входят.
- Мастера в приложение не заходят: их карточки ведёт менеджер.

## Этапы

### Этап 0 — подготовка (выполнено)

- Миграция `0022_crm_foundation.sql`: `organizations.timezone`,
  `organization_modules`, `audit_log`.
- `requireAuth` при каждом запросе перечитывает пользователя (кэш 30 с):
  деактивированный сотрудник и приостановленная организация теряют доступ
  сразу, а не через 30 дней; роль и организация берутся из БД.
- `requireModule(key)`, `GET /api/modules` — включённые модули организации.
- Платформенный админ: `GET /api/platform-admin/organizations/:id/modules`,
  `PUT /api/platform-admin/organizations/:id/modules/:key` `{ enabled }`.
- Организацию, в которой когда-либо включался модуль, удалить нельзя (409).
- Тесты: `cd backend && npm test` (vitest).

### Этап 1 — база данных CRM (написано, на ревью, в Supabase не применено)

- `0023_crm_core.sql` — настройки, нумерация, роли, справочники (источники,
  кампании, категории услуг, прайс), клиенты, заявки и их история статусов,
  сообщения, автомобили, сотрудники, правила процентов, заказы (услуги,
  мастера с долями, материалы, фото, комментарии, история).
- `0024_crm_finance.sql` — кассы, категории расходов, курсы валют, журнал
  денежных операций, начисления зарплаты, интеграции, вебхуки, подписки на
  уведомления.
- `0025_crm_functions.sql` — защитные триггеры и функции:
  `crm_record_order_payment`, `crm_reverse_transaction`, `crm_issue_order`,
  `crm_reopen_order`, `crm_seed_organization`.
- Тесты базы: `test/db/` — все миграции прогоняются в PGlite (Postgres в
  процессе Node), живая база не используется.

Правила, которые гарантирует сама база:
- данные разных организаций не могут ссылаться друг на друга;
- журнал денег и начислений нельзя изменить или удалить — только сторно;
- оплата заказа меняет `paid_amount` только через функцию, в одной транзакции;
- переплата, возврат больше оплаченного, скидка больше суммы — отклоняются;
- выданный заказ заморожен; отмена с оплатами запрещена до возврата;
- выручка, себестоимость и проценты мастеров фиксируются в момент выдачи в
  базовой валюте; изменение правил процентов не меняет прошлые начисления;
- приоритет правил: мастер×категория > мастер > категория > общее.

## Развёртывание

Миграции применяются вручную в Supabase SQL Editor по порядку номеров.
**Миграцию нужно применить до деплоя бэкенда**, который её использует.
